# Popup realization and rapid window-menu reopening

The 45e18f3 host run still failed: its selector trace retained 14 transitions but forwarded none. A native popup is outside the selector's ordinary layout branch, so listening only to the ComboBox's LayoutUpdated was insufficient. DockComboBox now observes the popup child's layout/loading and generated item loading, coalescing a single dispatcher continuation after native layout. Original navigation events are delivered at most once when native items exist. This is event-driven readiness, not timer polling or a synthetic selection algorithm. Close/source/unload generations invalidate obsolete continuations. The original twelve metadata-dependent immediate-key cycles and six Escape/reopen cycles remain unchanged.

A separate trace failed while reopening a window system menu 17 ms after Escape. Uno FlyoutBase.RemoveFromOpenFlyouts queues Closed and then hides the first remaining open flyout. Creating the next menu before this cleanup can therefore dismiss the new menu. WindowControl now retains the closing menu until Closed, records at most one replacement anchor, and opens the replacement in a dispatcher continuation after that native cleanup. Generation, loaded-owner and XamlRoot checks still prevent stale commands after manager/frame replacement.

Six extra rapid Escape/reopen pairs are exercised inside the existing maximized Move/Size case, with no readiness wait between Escape and the next opening click. Caption/native input behavior is unchanged, and no browser assertion is removed or relaxed. The complete candidate still defines 108 product cases plus the separate 100-cycle focus stress gate. Exact-head artifacts determine passing execution; neither earlier subsets nor compilation alone establish readiness.

Primary implementation references are Uno ComboBox's generated-container and popup key code and FlyoutBase.RemoveFromOpenFlyouts/ShowAtCore at upstream commit 951b7b464b8372daa95dae6eeedf9ac6c8109b90. No vendor source or assets are redistributed.
