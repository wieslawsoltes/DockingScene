# Floating translation paint review

The corrected-input head 2b9555c passed all 137 product browser cases, including the earlier border-capture and Escape failures. Inspection of the actual floating gap screenshots nevertheless showed the source still painted at x=20. The same trace reported model/frame x=69 and a correctly translated title hit target. This was not a model transaction or delayed diagnostic issue: the retained painted content and interactive geometry diverged. The green run was not merged after this finding.

Docking window and container placement now uses one retained native TranslateTransform per visual, leaving Canvas placement at zero. Width and height still perform ordinary layout, and any existing consumer RenderTransform remains composed inside the placement transform. This sends movement through the native composition transform path instead of relying only on changed arrange offsets of cached subtrees. The splitter-preview path uses the same placement function, so its live layout does not double-apply coordinates. DockDragOverlay preview/guide visuals also reuse native placement transforms. No opacity flicker, forced theme change, visual reparenting, polling redraw, browser script or global rendering-cache disable is used.

The existing whole-host and configured-gap scenarios now assert actual painted destination caption/content pixels and cleared vacated pixels, in addition to model, frame, split, editor and capture checks. These assertions reject the preceding screenshot, which still painted the old rectangle. The 137 scenario count remains unchanged; its visual assertions are stronger. Exact corrected-head builds, packages, all product/focus tests and final PNG inspection are required before merge.

The placement helper preserves visual, editor, template and transform identities across unchanged projections. Only changed positions update the native translation. It is not a full compositor performance measurement or vendor pixel-equivalence claim. Existing application transforms remain supported; Canvas attached coordinates are an implementation detail of these library-owned frame/container positions.

Primary implementation reference: Uno Canvas.OnLeftChanged/OnTopChanged invalidate arrangement, while native Visual distinguishes arrange-offset and transform updates.
